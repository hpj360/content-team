# 资产一致性审查法（设定库级体检）

> `novel-writing` 按需加载参考。蒸馏自项目实战中反复使用的"资产一致性审查"流程，沉淀为通用方法。
> **分工**：稿件文字体检（结构/场景/句层，钩子与节奏）→ `script-writing/references/revision-diagnosis.md`；
> 伏笔对账与状态落盘 → `story-state-and-continuity.md` + `GET /api/novels/{id}/story-state`；
> **本篇只管设定资产之间**的交叉一致性：档案、时间线、称谓、地图、数值、伏笔账彼此对账，
> 回答"两个设定文件（或设定与正文）说的同一件事，是不是同一件事"。
> 校准 2026-11-15 · 示例全部自造（云港/潮晶/鳞阶等均为虚构），不含任何作品专名。

## 一、审什么（六类资产）

审查以资产为单位推进。每类资产先确认**单一事实源**（唯一权威文件），再列出该类最高发的不一致形态：

| 资产类 | 单一事实源 | 高频不一致 |
|---|---|---|
| 人物（档案/正文出场） | `character-bible.md` 档案 + `StoryState.characters` 四维状态 | 外貌识别符漂移；能力/心理跨卷突变；称呼进度条跳阶无事件 |
| 纪年（时间线/正文提及） | 拆库时间线 + 逐章记录 | 年龄随章漂移；事件先后矛盾；季节/昼夜与剧情不符 |
| 称谓与 ID | 人物档案"全员称呼表"（改口章号登记进状态卡） | 同一人多称呼混用；无事件改口；代号与真名错位 |
| 地理与空间 | 世界观档案地理层（`worldbuilding-guide.md`） | 两地距离/耗时前后不一；方位颠倒；同名异写 |
| 体系数值（境界/价格/等级） | `power-system-design.md` 兑换表与主数值刻度 | 兑换率漂移；越阶无代价；评级滞后不收敛 |
| 伏笔账 | `伏笔.md` 派生视图 + story-state API 字段 | 登记状态与正文进度脱节；已回收未标注；埋设位置对不上 |

取值口径：事实源写"基准值"，正文抓"提及值"；基准值必须落在文件里（不是作者记忆里），
与 `story-state-and-continuity.md` 的原则同源——**状态连续性靠落盘，不靠记忆**。

适用时机：新开卷、多人协作交接、长篇返场续写。三类场景下资产改动最密集、漂移风险最高，
审查收益最大；日常逐章写作不必每章跑全流程，按第三节的节奏抽查即可。

## 二、审查五步

五步是串行流水：跳步会让差异无法归因，乱序会让处置失去依据。

### ① 定事实源

- 六类资产逐类指定唯一权威文件，写进项目状态卡的全局约束栏；
- 冲突裁决规则只有一条：**以事实源为准**，正文与事实源矛盾即正文错（除非走第⑤步"口径升级"回写事实源）；
- 一个类目只允许一个事实源，出现两份权威时先合并再开审，否则对账结果不可信；
- 事实源本身要登记到节级："体系数值以 `power-system-design.md` 兑换表为准"——
  让任何后来者都能复核，而不是依赖当次会话的记忆。

### ② 逐项抽取

- 从正文/分卷抓"提及"：凡是与某类资产相关的字面陈述（年龄、价格、距离、称呼、境界）逐条摘出；
- 做成对账表，固定四列：`项 | 事实源值 | 正文值 | 出处行`——出处必须到行/章，不许写"大概在第 3 卷"；
- 抽取范围按第三节节奏定：轻审只抽数量可控的两类，全量审六类都抽；
- 抽取用检索词清单代替目测：人名全量、货币名、境界名、地名，逐词全文检索，防漏防错记。

### ③ 交叉比对

- **数值类精确比对**：境界序号、货币数额、距离里程逐字核对，"差不多"不算通过；
  兑换表类（一枚潮晶=三日修炼）重点核对跨卷是否漂移（对应 S2 失效信号）；
- **称谓类全量比对**：每个角色在每个章节被叫过什么，全列出来核对；
  改口必须有事件触发（对应 `character-bible.md` 5.2），无事件的改口即差异；
- 比对输出只有两态：一致 / 不一致。拿不准的按不一致处理，进第④步归因；
- 抽取与比对分离：先把该类全部提及抽完再统一比对，边抽边比容易漏掉同类项。

### ④ 差异归因

每条不一致归入三类之一，归因决定处置方向：

| 归因类 | 典型成因 | 默认处置方向 |
|---|---|---|
| 笔误 | 生成时误写、错字、串号 | 修正文 |
| 改稿未回写 | 改了正文（或档案）但另一侧没跟上 | 补一侧回写，保持两侧一致 |
| 口径升级未同步 | 作者有意改设定（数值重定/人物改名） | 回写事实源，正文不动 |

### ⑤ 台账处置

- 每条差异三选一处置：**回写事实源**（口径升级）/ **修正文**（笔误、未回写）/ **登记"可容忍差异"**（刻意留白的模糊地带）；
- "可容忍差异"必须写明容忍理由（如"旁白取整 vs 档案精确值"），禁止用其掩盖真矛盾；
- 每条处置都给 **owner 与回合**（谁在哪一轮修），台账不留无主悬账；
- 处置完成后复跑一次②③，确认差异清零且未引入新差异；
- 台账可与 `revision-diagnosis.md` 的修订台账同轮存放：资产回写与文字修订在同一修订轮执行，
  复跑验收也共用同一时点，避免"文修好了、设定又漂了"的来回扯皮。

## 三、抽查节奏

- **每 N 章一次轻审**（N 按卷长定，建议 10）：只查**称谓 + 纪年**两类——它们提及密度最高、漂移最快、机器最易比对；
- **大事件后必重审**：死亡、突破（境界跳档）、换地图（进入新城/新境）三类事件后，对应资产类全量重抽一遍；
- **交稿前全量审**：六类资产全量对账，作为与 revision-diagnosis 三层体检并列的最后一道门；
- 轻审发现的问题立即进台账，不积压到全量审——积压会让归因失去上下文；
- 节奏可自适应：连续两轮轻审零差异，可将 N 上调一档；一旦出现人物生死这类
  P0 级差异，立即放弃轻审、改跑全量。

## 四、对账表模板（可直接抄用）

| 项 | 类别 | 事实源值 | 正文值 | 出处 | 归因 | 处置 |
|---|---|---|---|---|---|---|
| 主角年龄 | 纪年 | 27 岁（开篇基准） | 28 岁 | 第 9 章 L12 | 改稿未回写 | 修正文为 27 岁 · owner: drafter · 回合 2 |

填写纪律：`出处`精确到章与行；`归因`只用第④步的三类名；`处置`必须含 owner 与回合，
与 `revision-diagnosis.md` 的修订台账同口径——**宁可多记，不可省略**。
一行一条差异，同一项在不同章节漂移出不同值时拆成多行，不合并——合并会让归因失真。

## 五、高频陷阱（8 条）

1. **年龄随章漂移**：时间线只过了三个月，旁白却长了一岁。归因多为笔误；重审必查纪年类。
2. **伤势凭空痊愈**：上一章断臂，下一章握剑无交代。查人物状态四维记录，离开状态必须与正文对齐。
3. **死而复生无解释**：伏笔账标"已回收"，正文却让人复活。生死属大事件，重审后仍须给机制或撤回。
4. **钱与物品无来源**：主角突然拿得出一件越阶造物。查兑换表与产出闭环（S5），无来源即补埋点或删物。
5. **称谓前后不一**：同一章内"云港主/沈主/沈大人"混用且非刻意的多视角称呼。查全员称呼表，逐处统一。
6. **地图距离矛盾**：A 到 B 上卷三天、本卷当日达。查地理层基准值，未解释的耗时变化按笔误修。
7. **数值跳变无代价**：境界一夜连跳两档。查代价三要素（S3），跳变要么付代价、要么延档。
8. **伏笔登记与正文脱节**：账面"进行中"，正文早已回收；或账面"已埋"，正文找不到埋设句。以 story-state API 导出全量对一遍埋设位置。

速查口径：第 1/2/3/8 条属**大事件类**（触发第三节"大事件后必重审"）；第 4/5/6/7 条属**日常漂移类**（轻审节奏即可覆盖）。

## 六、与自动化：API 代查与人审的分界

现有 API 可代查的项交给机器，省下的人力只花在语义判断上。分界如下：

| 审查项 | 代查/人审 | 途径 |
|---|---|---|
| 伏笔状态（已埋/进行中/已回收）与计划回收位置 | 可代查 | `GET /api/novels/{id}/story-state` 伏笔字段全量导出比对 |
| 状态卡 7 栏完整性、角色四维记录有无 | 可代查 | `_tracking-state.json` 解析 + 门禁断言（T002–T004 等） |
| 书目、章节数、卷章结构 | 可代查 | 书目 API 与逐章记录文件比对 |
| 数值基准值 vs 正文提及值 | 半自动 | 正文抓取仍靠人（或检索），比对本身可脚本化 |
| 称谓全量清单生成 | 可代查 | 从称呼表导出清单，正文按清单逐词检索出现位置 |
| 年龄/纪年差值计算 | 半自动 | 基准值落档后，"当前章-开篇基准"的差值可脚本算出 |
| 称谓改口是否有事件触发 | 必须人审 | 涉及叙事语义，机器无法判定"这次改口算不算被触发" |
| 动机与情感连续性（为何此刻心态变了） | 必须人审 | 四维记录只记"变了什么"，"变是否可信"只能读 |
| 伤势/生死判定的剧情合理性 | 必须人审 | 状态落盘判"记录对不对"，本条判"剧情对不对" |
| 可容忍差异的裁量 | 必须人审 | 容忍是编辑决策，不能默认给机器 |

分界原则：**机器管"字段齐不齐、值等不等"，人管"值该不该是这个、变化可不可信"**。
复跑口径：API 导出以审查时点为准；处置回写后需再导一次确认，导出结果本身进台账留痕。

## 七、自检（6 条）

- [ ] 六类资产每类都指定了唯一事实源，且写进了项目状态卡
- [ ] 对账表每行都有精确出处（章+行），无"大概在哪一卷"
- [ ] 数值类做到逐字精确比对，称谓类做到全量比对（含配角）
- [ ] 每条差异都归因到三类之一，无"待定"积压
- [ ] 每条处置都有 owner 与回合，台账无主悬账为零
- [ ] 处置后复跑过一次抽取比对，确认清零且未引入新差异

## 八、局限（3 行）

1. 全量审查人工成本高，宜按第三节节奏抽查（轻审为主、全量仅在交稿前）；
2. 事实源缺失时先建档再审——没有权威文件，对账无从谈起，审查会退化成争吵；
3. 本篇只管资产间交叉一致性，不替代稿件文字体检（`revision-diagnosis.md`）与伏笔对账（story-state API），三道门并行不互替。
